# ✈ Personalized Travel Planner (Java + JavaFX)

A desktop app that builds a **day-by-day travel itinerary at runtime** from your destination, budget,
number of days, travelers, interests and travel pace. Places come from real OpenStreetMap data,
travel distances from OpenRouteService, and every decision (scoring, budget, ordering, timing) is
made by plain Java code in `TravelPlanner.java`. **Nothing is hard-coded per city.**

## 2. Get a free OpenRouteService (HeiGIT) API key

1. Go to the OpenRouteService / HeiGIT dashboard: <https://openrouteservice.org/dev/#/signup> and create a free account.
2. Open **Dashboard → Tokens**, create a token (the free "Standard" plan is enough).
3. Copy the key.

### Where to paste it

In the **project root** (the same folder as `pom.xml`):

```
copy config.properties.example config.properties      (Windows)
cp   config.properties.example config.properties      (Mac/Linux)
```

Then edit **`config.properties`**:

```properties
ORS_API_KEY=paste_your_key_here
SEARCH_RADIUS_KM=12
```

`config.properties` is in `.gitignore`, so your key is never committed.
**Without a key the app still works** (offline mode: estimated distances, no live suggestions).

## 4. APIs used and why

| API | Key? | Used for |
|---|---|---|
| **HeiGIT Pelias Search** `api.heigit.org/pelias/v1/search` | ORS key | Destination / start location → coordinates + country |
| **HeiGIT Pelias Autocomplete** `api.heigit.org/pelias/v1/autocomplete` | ORS key | Live suggestions while typing (400 ms debounce, min 3 letters) |
| **ORS Matrix** `api.heigit.org/openrouteservice/v2/matrix/driving-car` | ORS key | Road distance + time between **all** candidate places in **ONE request** |
| **Overpass API** (OpenStreetMap) `overpass-api.de` (+ mirror `overpass.kumi.systems`) | none | Finding **real places** (beaches, forts, museums, restaurants…) by interest tags |
| **Nominatim** (OpenStreetMap) | none | Backup geocoder, only if HeiGIT fails (max 1 request/second) |
| **Wikipedia REST summary** | none | One-line description for the places that end up in the itinerary |
| **Wikidata** `wikidata.org/w/api.php` | none | Fame score: how many Wikipedia languages cover a place (ranking) |
| **open.er-api.com** | none | INR → local currency, for display only (e.g. "≈ €12" in Paris) |
| **Photon** `photon.komoot.io` | none | Fast suggestions while typing (OpenRouteService autocomplete is the backup) |
| **CARTO map tiles** (OpenStreetMap data) | free key, optional (`CARTO_API_KEY`) | Background map. Since Aug 2026 CARTO watermarks tiles requested without a key; with no key the app uses the standard OpenStreetMap tiles instead |

ORS is a routing service, not a database of tourist places, which is why place discovery uses Overpass.
The Directions API is left as a documented stub in `OpenRouteServiceClient` (future work).

## 5. Fallbacks (the app never crashes on an API failure)

| What fails | What happens |
|---|---|
| **Matrix API** (no internet, bad key, rate limit) | Distance = straight-line (Haversine) × 1.3 road factor, time at 35 km/h. Items are marked "≈ … km (est.)" and a yellow banner explains it. |
| **Overpass** | Retry once on the mirror → on-disk cache → `fallback_places.json` (small demo list for Goa, Paris, Chennai) + "Using offline demo data" banner. The itinerary is **still generated by the algorithm**. |
| **Geocoder** | HeiGIT → Nominatim → demo city list → friendly error "We couldn't find that destination…" |
| **No / placeholder API key** | Blue notice on the form, app runs in offline (Haversine) mode. |
| **Wikipedia / currency / autocomplete** | Silently hidden (generic description, no "≈ €" equivalents, no suggestions). |

**Caching:** geocoding, Overpass, Matrix, Wikipedia and exchange-rate answers are stored as JSON files
in `cache/`. Repeat searches are instant and work offline, which makes the demo reliable.
Use the **🗑 Clear cache** button (top right of the form) to fetch fresh data.

## 6. How the algorithm works (for the viva)

All of this lives in `TravelPlanner.java`, and all estimate constants are in one block at the top of it.

1. **Candidate collection**: geocode the destination, then ask Overpass for named places whose OSM tags
   match the selected interests (e.g. Beaches → `natural=beach`, History → `historic=fort|monument|…`),
   plus general `tourism=attraction`. Well-known places (with a Wikidata entry) are requested first.
   Duplicates (same name, same Wikidata ID, or the same landmark mapped twice) are removed.

2. **Cost + duration estimate**: base cost per person by category in INR (beach ₹0, museum ₹150,
   fort ₹100, restaurant ₹400, spa ₹1500…) × a **country cost factor** (India 1.0, France 3.5, UK/US 4.0…)
   × travelers. Local transport = km × ₹15 per vehicle. Everything is labelled **"est."**.

3. **Fame + scoring** (simple and explainable):
   - **Fame** comes from **Wikidata**: the number of Wikipedia language editions with an article about
     the place (OpenStreetMap has no star ratings). Bangalore Palace has dozens, a small junction a few.
     The destination's landmarks (parks, palaces, museums, temples…) are always searched, whatever
     interests are ticked, and the city's **5 most famous** places are flagged as must-see.
   - **+50** per matching interest (max 2 counted)
   - **+0…45** fame (log scale), **+30** if must-see, **+10** website/attraction hint if fame is unknown
   - **+20** if cost ≤ 30% of the per-person daily budget, **+10** if ≤ 50%
   - **+10** if it suits the pace (Relaxed → beaches/parks/spas/cafés, Packed → short visits,
     Moderate → history/culture)
   - **−0…20** the further it is from the city centre; **−30** if the name has no Latin letters

   Then `Collections.sort` by score, highest first.

4. **One Matrix request** for the best ~20 candidates gives the road distance/time between every pair
   (never one request per pair).

5. **Greedy nearest-neighbour day building** (not TSP):
   - The pace sets the day shape with a `switch`: Relaxed 2-3 stops from 10:00, Moderate 3-4 from 9:30,
     Packed 5-6 from 9:00.
   - Each day starts with the **highest-scoring unused place**. The next stop is the one maximising
     `score − 4 × km − 15 × (same category already today)`, i.e. good, close and varied.
   - **Budget guard:** before adding any place we check `runningTotal + cost ≤ today's budget`.
     The remaining budget is split evenly over the remaining days, unspent money rolls over, and
     money for lunch is kept aside. If a place doesn't fit, cheaper alternatives are tried. If the
     budget runs out the plan is shorter and a note says *"Your budget only covered N activities."*
   - **Time guard:** a stop must end before the day ends (~7-8 PM).
   - **Lunch** (after 12:00, never before 12:30) is the best nearby affordable restaurant, so
     closeness counts double. If the user picked Food, dinner is added at 7 PM.

6. **Scheduling**: `arrival = previous end + travel time + buffer`, `end = arrival + visit duration`,
   formatted as "10:00 AM".

| `PlaceSearchException`, `DestinationNotFoundException` | Custom exceptions |
| `OpenRouteServiceClient` | HeiGIT geocode, autocomplete, matrix |

| `FallbackData` | Reads `fallback_places.json` (demo data only) |

Threads: a JavaFX `Task` runs the whole planning in the background, so the window never freezes and
can show progress. Inside the planner a thread pool (`ExecutorService`) runs independent network calls
at the same time (start-location lookup, fame batches, all place descriptions), and `OverpassClient`
races the main server against the mirror when the main one is slow.

## 8. Java concepts map (for the viva)

| Concept | Where to show it |
|---|---|
| Classes, objects, constructors, encapsulation | `Place`, `UserPreferences`, `Itinerary` (private fields + getters/setters) |
| **Inheritance** | `ActivityItem` / `MealItem` **extend** `ItineraryItem`; `WikipediaClient`, `WikidataClient`, `NominatimClient`, `OverpassClient`, `OpenRouteServiceClient` **extend** `ApiClient`; `Main extends Application` |
| Constructor chaining (`super`) | every `ApiClient` subclass calls `super("service name")`; `MealItem` calls `super(...)` then sets its own field |
| **Abstract class** | `ApiClient` (abstract `getPurpose()`, shared caching), `ItineraryItem` (abstract `isMeal()`, `getLabel()`) |
| **Interfaces** | `PlaceProvider` (Overpass, offline data), `Geocoder` (HeiGIT, Nominatim, offline data); `default` method `isOfflineData()` |
| **Runtime polymorphism** | `TravelPlanner.locate()` loops over `List<Geocoder>`; `fetchPlaces()` loops over `List<PlaceProvider>`; `FileManager` calls `item.getLabel()` |
| Method overriding (`@Override`) | `getLabel()`, `isMeal()`, `getPurpose()`, `toString()`, `shouldCache()` hook |
| Method overloading | `OverpassClient.findPlaces(...)` (two versions); `TravelPlanner.generate(...)` (two versions) |
| **Enum** with constructor/fields/methods | `Pace` (`RELAXED`, `MODERATE`, `PACKED`, `fromLabel()`, `suits()`) |
| Exceptions: try/catch/finally, multi-catch, throws | everywhere; `finally` in `TravelPlanner.generate()` and `OverpassClient.raceServers()` |
| **Custom exceptions** | `PlaceSearchException` (checked), `DestinationNotFoundException` (unchecked) |
| **Multithreading** | JavaFX `Task` (`Main`, `PlanningView`); `ExecutorService` + `Future` (`TravelPlanner`); `ExecutorCompletionService` (`OverpassClient`); `synchronized` (`NominatimClient`), `volatile` (`ApiClient`), `Collections.synchronizedMap` (`OpenRouteServiceClient`) |
| Collections & generics | `ArrayList`, `HashMap`, `LinkedHashMap`, `HashSet`, `List<Future<Map<String,Integer>>>` |
| Lambdas / method references | `pool.submit(() -> ...)`, `Comparator.comparingDouble(Place::getScore)` |
| File I/O, try-with-resources | `FileManager` (save .txt), `CacheManager`, `ConfigLoader` |
| Static members / static initializer block | `ItineraryItem.formatTime()`, `OverpassClient.LANDMARK_FILTERS` |

## 9. Automated tests (JUnit 5)

Run them with **`test.bat`** (Windows, double-click) or `mvnw.cmd test` / `./mvnw test`.
The first run downloads JUnit (a few MB). All tests run **offline** in a few seconds.

| Test class | What it checks |
|---|---|
| `TravelPlannerTest` | right number of days, **never over budget**, pace limits, activities end on time, lunch not before 12:30, no overlapping stops, no place twice, unknown destination error, fallback to the next place source, small-budget note, offline estimates |
| `UserPreferencesTest` | every form validation rule (empty fields, 1-14 days, budget, travelers, interests) |
| `PaceTest` | the `Pace` enum: text conversion, defaults, sensible settings, `suits()` |
| `ItineraryItemTest` | time/duration formatting, **polymorphism** of `ActivityItem` vs `MealItem` |
| `HaversineUtilTest` | straight-line distance formula (e.g. Bangalore-Chennai about 290 km) |
| `TransportEstimatorTest` | which transport types are offered, return prices for the group, cars per group, one recommendation |

**How the planner is tested offline (viva point):** `TravelPlanner` receives its geocoders and place
providers through its constructor (*dependency injection*). The app passes the real API clients; the
tests pass small fake classes from `TestData.java` that implement the same `Geocoder` and
`PlaceProvider` interfaces and return a made-up city. So the tests never touch the internet and always
give the same result, which is only possible because of the interfaces.

## 10. User interface

- **Planning screen** looks like a travel ticket: *From → To* on top, a tear-off line, then days,
  travellers, budget, interest toggles and a pace selector (with a hint like "3-4 places a day").
- **Result screen** is split: the day-by-day **timeline** on the left (numbered stops, travel time
  between them, must-see badges, collapsible days, a costs panel with a budget bar) and an
  **interactive map** on the right. The chips above the map switch between all days and one day;
  each day has its own colour, and the numbers on the map match the numbers in the timeline.
- **Getting there and back**: flight / train / bus / car options for the journey from the start city,
  with travel time and a rough return price for the whole group (per-km fares; a recommendation is
  the cheapest option under 12 hours). Picking one adds it to the costs panel as a grand total
  (activities + journey) compared with the budget; the activity plan itself stays the same.
- **Dark mode**: button in the top bar; the choice is remembered (Java `Preferences`).
- Colours are CSS variables in `style.css` (`.root` for light, `.root.dark` for dark).

The map's lines connect the stops in visiting order (straight lines); the travel times shown in the
timeline come from the road matrix. Map tiles need an internet connection.
